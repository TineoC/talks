❯ clarification

Free software ≠ Open source

Two overlapping but distinct philosophies. Same code, different why.

Free software

A movement

  • User freedom as the goal
  • FSF · 1985 · Richard Stallman
  • Four freedoms (run, study, modify, share)
  • License ethos: copyleft
≠

Open source

A methodology

  • Practical benefits as the goal
  • OSI · 1998 · Raymond & Perens
  • 10 Open Source Definition criteria
  • License ethos: permissive

Most projects are both. The difference is the why, not the what.

This is the intellectual setup for the rest of the talk. Two different terms, two different communities, two different values frames. They overlap on the code (most FLOSS is both), but diverge on the *why*. "Free software" is a moral stance: the user has rights. "Open source" is a practical stance: sharing the code makes better software. Both arrive at similar licenses, but the *conversation* about sustainability differs depending on which camp you came from. The talk title uses "Free Software" deliberately — the moral frame. The "Open source" frame comes in the cost sections. [TIMING: 90s. Don't dwell. Move on to the Stallman slide where the etymology actually lands.]

"Free" as in beer vs "free" as in speech

Stallman chose "free" to mean freedom (speech), not price (beer).

The English language has only one word for both, causing 40 years of etymological confusion.

This talk is about the gap between them — and who pays for it.

Two important things to land here. 1. The image. Stallman is the originator of the framing that gave us the title. Showing his face makes the etymology real, not abstract. Caption already includes the credit per CREDITS.md. 2. The "free as in beer / free as in speech" line. This is the canonical quote, used in every OSS talk ever. Lean into the familiarity — the audience has heard it before, but the rest of the talk will give that line a price tag. Act 04

The Solution

Stop calling it free. Start treating it like infrastructure.

[TIMING: 15s. Pivot. We've named the problem. Now we hand them a framework.]

Open source is critical infrastructure

If 70–90% of your code is open source, dependencies are your infrastructure.

And we already know how to treat critical infrastructure:

Monitor

Watch for advisories, EOL announcements, maintainer health signals.

Set SLOs

Define what "healthy" means for each critical dependency.

Staff it

Assign owners. Budget time. Treat maintainer relationships as a critical asset.

The reframing is the talk's pivot. "Open source is critical infrastructure" is a sentence the audience's brain can already file under "things I know how to operate." That's the whole trick: we're not asking them to learn a new discipline. We're asking them to apply the discipline they already have. The three cards (Monitor / SLOs / Staff) are the vocabulary of their day jobs, applied to OSS dependencies. Each one is a thing they already do for internal services. [TIMING: 2 minutes. The pivot should feel like relief, not work.]

A four-step framework

01 · Discover

Discover

What are you actually depending on? Generate a complete SBOM. Know your transitive graph.

02 · Assess

Assess

For each critical dependency: how many maintainers? Who funds it? Is there a bus factor of one?

03 · Fund

Fund

Direct sponsorship, GitHub Sponsors, Open Collective, foundation dues, Tidelift — pick at least one per critical dep.

04 · Contribute

Contribute

Time, code, reviews, documentation, security disclosures. The most valuable currency isn't money; it's attention.

Run this loop quarterly: Discover → Assess → Fund → Contribute

This is the talk's deliverable. Everything before this is setup. The four steps are deliberately concrete: each one is something a platform team can put on a sprint board. Common audience questions to anticipate: - "We don't have budget for sponsorship." → That's why Contribute matters. Time is a budget too. - "What if the project is hostile?" → That's an Assess output. Factor it into your decision. - "This sounds like a lot of work." → It is. The alternative is the bill from the previous act. [TIMING: 3 minutes. This is the longest content slide. Walk each step slowly. This is the slide they photograph.]

Act 05

The Action

What you do on Monday morning.

[TIMING: 15s. Last act. This is the call to action. Make it specific and short.]

What you do on Monday

If you lead engineers

  • Add OSS sustainability to your budget conversation.
  • Fund at least one maintainer or foundation this quarter.
  • Recognize internal OSS contribution as real work in performance reviews.

If you're on a platform / SRE team

  • Keep track of your SBOMs
  • Tag your top transitive dependencies and keep track of the lottery factor.
  • Open issues upstream before you open them internally.

If you're an individual contributor

  • Pick one dependency you use every day. Read the issues. Star the repo.
  • Submit one PR this month — docs count.
  • Pay for the maintainer's work if they accept money.
Three columns, three audiences. The segmentation matters because the right next step depends on your role. Don't say "everybody should fund maintainers" — leaders fund, ICs contribute time, SREs assess and route. The "if you're an individual contributor" column is the most underestimated. ICs are the largest audience in the room and the most likely to act. Make their action feel small and concrete. [TIMING: 2 minutes. Don't read the bullets. Tell a one-line story for each column instead.]

❯ terminal

Tagging & tracking with gh / glab

GitHub CLI (gh)

# Loop all repos & fetch transitives (Free)
$ for repo in $(gh repo list --limit 100 \
    --json nameWithOwner -q '.[].nameWithOwner'); do
    gh api repos/$repo/contents/package-lock.json \
      -H "Accept: application/vnd.github.raw" | \
      jq -r '.packages | keys[] | select(. != "")'
  done

# Bulk check Lottery Factor (>10 contributors)
$ for repo in $(gh repo list --limit 100 \
    --json nameWithOwner -q '.[].nameWithOwner'); do
    gh api repos/$repo/contributors \
      --jq '[.[] | select(.contributions > 10)] | length'
  done

GitLab CLI (glab)

# Loop all projects & fetch transitives (Free)
$ for repo in $(glab repo list -F json | \
    jq -r '.[].path_with_namespace'); do
    enc="${repo//\//%2F}"
    glab api projects/$enc/repository/files/package-lock.json/raw | \
      jq -r '.packages | keys[] | select(. != "")'
  done

# Bulk check Lottery Factor (>10 commits)
$ for repo in $(glab repo list -F json | \
    jq -r '.[].path_with_namespace'); do
    enc="${repo//\//%2F}"
    glab api projects/$enc/repository/contributors | \
      jq 'map(select(.commits > 10)) | length'
  done
Lottery factor (or bus factor) is defined as the number of key developers who must be run over by a bus (or win the lottery) before the project halts. You can automate this via CLI scripts querying the API. Active contributors can be estimated by filtering for users with >10 contributions/commits in the repository history.
