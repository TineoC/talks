☁️ What is Cloud Native?

📋 CNCF Definition

"Cloud native technologies empower organizations to run scalable applications in dynamic environments — containers, service meshes, microservices, immutable infrastructure, and declarative APIs."

— Cloud Native Computing Foundation

5,300+ 👥 CNCF ecosystem contributors
185+ 📊 CNCF projects across the landscape
96% 📈 of organizations use or evaluate containers

⚡ Cloud Native ≠ "running workloads in someone else's datacenter"

The CNCF definition is the official answer. Break it down: containers, microservices, declarative APIs. The numbers give scale. The punch line: cloud native is about HOW you build and operate, not WHERE you run. [TIMING: 2 min]

Containers vs Virtual Machines

❯ docker run -d -p 8080:80 nginx

# ~500ms later, Nginx is running and available

The key insight: VMs virtualize hardware, containers virtualize the OS. Containers share the host kernel, which makes them lightweight and fast. This is what enables the density and velocity that cloud native promises. [TIMING: 2 min]

Containers

🐳 Container Images

An image is a read-only template with instructions for creating a container.

❯ docker pull nginx:latest

❯ docker images

REPOSITORY   TAG    IMAGE ID     SIZE
nginx       latest   abc123     192MB

❯ docker run -it nginx /bin/bash

root@a1b2c3:/# I'm inside a container!

🧅 Image Layers

Images are built in layers. Each Dockerfile command creates a new layer. Layers are cached and shared between images.

CMD ["nginx", "-g", "daemon off;"]
COPY app/ /var/www/
RUN apt install -y nginx
FROM ubuntu:latest ← cached & shared

❯ docker pull ubuntu:latest   # cached

❯ docker build -t my-app .   # reuses cached layers

Images are the "source code" for containers. They're layered, cached, and distributed through registries. The Dockerfile is the recipe. Show the commands but don't go deep — this is a 101, not a Docker deep-dive. [TIMING: 3 min]

One container is easy. A hundred is not.

Kubernetes Architecture

A Kubernetes cluster has two planes:

☸️ Control Plane

API Server · etcd · Scheduler · Controller Manager

The brain of the cluster.

🔧 Worker Nodes

kubelet · kube-proxy · Container Runtime

Where workloads actually run.

❯ kubectl get nodes

NAME       STATUS   ROLES    AGE talos-cp    Ready   control-plane 12m talos-w1    Ready   worker     10m

The architecture is simple: control plane makes decisions, workers run the containers. kubelet is what Kubernetes installs on each node to manage containers. The API server is the only thing you talk to directly. [TIMING: 2.5 min]

📦 Pods

The smallest deployable unit in Kubernetes.

A Pod wraps one or more containers, sharing:

  • 🌐 Network namespace (same IP)
  • 💾 Storage volumes
  • 🔄 Lifecycle (started/stopped together)

💡 Key insight

You never run "naked" Pods in production. Deployments manage them for you.

❯ cat pod.yaml

apiVersion: v1 kind: Pod metadata: name: my-app spec: containers: - name: app image: nginx:latest ports: - containerPort: 80

Pod is the atomic unit. One Pod = one IP. Containers inside a Pod share that IP and can communicate via localhost. But you almost never create Pods directly — Deployments are the production-level abstraction. [TIMING: 2 min]

🔄 Deployments

Declarative updates for Pods.

A Deployment tells Kubernetes: "I want 3 replicas of this Pod, and here's the image to use."

  • 🔄 Rolling updates — zero-downtime deploys
  • ⏪ Rollback — revert to a previous revision
  • 💚 Self-healing — recreates failed Pods
  • 📈 Scaling — kubectl scale changes replica count

❯ kubectl scale deployment frontend --replicas=3

❯ kubectl rollout status deployment/frontend

❯ cat deployment.yaml

apiVersion: apps/v1 kind: Deployment metadata: name: frontend spec: replicas: 2 selector: matchLabels: app: frontend template: metadata: labels: app: frontend spec: containers: - name: server image: ghcr.io/tineoc/online- boutique-frontend:galaxygate ports: - containerPort: 8080 readinessProbe: httpGet: path: /_healthz port: 8080

Deployments are the workhorse of K8s. They manage ReplicaSets, which manage Pods. The selector/label system is how K8s tracks ownership. Show the YAML structure: replicas, selector, template. This is what we'll deploy in the demo. [TIMING: 2.5 min]

🌐 Services

Stable networking for dynamic Pods.

Pods come and go. A Service gives them a stable DNS name and IP.

🏠 ClusterIP

Internal only.

🚪 NodePort

Static port on every node.

🌍 LoadBalancer

Cloud LB integration.

🔗 Headless

For stateful workloads.

❯ kubectl get svc -n online-boutique

NAME            TYPE       CLUSTER-IP   PORT(S) frontend        ClusterIP   10.0.0.1   80/TCP frontend-external LoadBalancer 10.0.0.2   80:32001/TCP redis-cart       ClusterIP   10.0.0.3   6379/TCP productcatalog   ClusterIP   10.0.0.4   3550/TCP

Services decouple Pod IPs from stable endpoints. When a Pod dies and gets recreated with a new IP, the Service still routes traffic. The selector label system is key: Service routes to Pods whose labels match. [TIMING: 2 min]

🔐 ConfigMaps & Secrets

⚙️ ConfigMap

Non-sensitive configuration.

apiVersion: v1 kind: ConfigMap metadata: name: app-config data: DATABASE_HOST: "postgres.prod.svc" LOG_LEVEL: "debug"

🔒 Secret

Sensitive data (base64 encoded).

apiVersion: v1 kind: Secret metadata: name: app-secrets type: Opaque data: DB_PASSWORD: cGFzc3cwcmQ= API_KEY: MTIzNDU2Nzg5MA==

Injected as environment variables or mounted as volumes. Secrets are base64, not encrypted by default — use external secret stores in production.

ConfigMaps and Secrets decouple configuration from container images. Same image, different config per environment. Note that Secrets are only base64 encoded — not encrypted. For production, use something like External Secrets Operator or Vault. [TIMING: 1.5 min]

# Create resources from YAML

❯ kubectl apply -f k8s/

# Describe resources (verbose)

❯ kubectl describe pod frontend-7d4f8f9b6-xk3c2

# Port-forward to access a service locally

❯ kubectl port-forward svc/frontend 8080:80

Pro tip: kubectl api-resources lists everything you can interact with

The most-used commands in one place. In the demo, we'll run most of these live. The pattern is always the same: kubectl <verb> <resource> [flags]. [TIMING: 1.5 min]
