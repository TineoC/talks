❯ clarification

Free software ≠ Open source

Two overlapping but distinct philosophies. Same code, different why.

Free software

A movement

  • User freedom as the goal
  • FSF · 1985 · Richard Stallman
  • Four freedoms (run, study, modify, share)
  • License ethos: copyleft
≠

Open source

A methodology

  • Practical benefits as the goal
  • OSI · 1998 · Raymond & Perens
  • 10 Open Source Definition criteria
  • License ethos: copyright

Most projects are both. The difference is the why, not the what.

Sources: FSF, "What is Free Software?" · OSI, The Open Source Definition

This is the intellectual setup for the rest of the talk. Two different terms, two different communities, two different values frames. They overlap on the code (most FLOSS is both), but diverge on the *why*. "Free software" is a moral stance: the user has rights. "Open source" is a practical stance: sharing the code makes better software. Both arrive at similar licenses, but the *conversation* about sustainability differs depending on which camp you came from. The talk title uses "Free Software" deliberately — the moral frame. The "Open source" frame comes in the cost sections. [TIMING: 90s. Don't dwell. Move on to the Stallman slide where the etymology actually lands.]

"Free" as in beer vs "free" as in speech

Stallman chose "free" to mean freedom (speech), not price (beer).

The English language has only one word for both, causing 40 years of etymological confusion.

This talk is about the gap between them — and who pays for it.

Two important things to land here. 1. The image. Stallman is the originator of the framing that gave us the title. Showing his face makes the etymology real, not abstract. Caption already includes the credit per CREDITS.md. 2. The "free as in beer / free as in speech" line. This is the canonical quote, used in every OSS talk ever. Lean into the familiarity — the audience has heard it before, but the rest of the talk will give that line a price tag. The fork tax

5,160 h

of rework every release cycle, just to keep private forks building. The average organization carries 86 forks × 60 hours.

≈ $258K at an assumed $50/hour. 37% of forks exist for security patches or compliance.

At Android scale

18 months from an upstream LTS kernel release to devices, with up to 50% of kernel code out of tree.
90% of Android kernel security issues were already fixed for devices that stayed current.

Google's fix: the Generic Kernel Image, and ChromeOS's "Upstream First" rule. The patch lands upstream before it ships.

Sources: Linux Foundation, "ROI for Open Source Software Contribution", Feb 2026 (fork questions n=238) · Android GKI docs · ChromeOS, Upstream First

New Sep 27 2026. This is the most realistic argument for the room: you are probably already paying for open source, just in the most expensive way, by carrying patches. Receipts: - LF ROI report (Feb 2026): "On average, an organization maintains 86 private forks … Each … requires 60 labor hours for maintenance and integration per release cycle." 86 × 60 = 5,160 hours. The $258K is the report's own estimate at an assumed $50/hour (Stack Overflow median wage), NOT reported spend. The fork questions had n=238 of the 567 responses. It scales with size: 147 hours for small orgs, 11,152 for orgs over 5,000 employees. Reasons for forking: custom features 54%, internal integration 44%, "security patches or compliance requirements" 37%. Aniszczyk's foreword: "Organizations that rely on internal patches without upstreaming them create private forks leading to technical debt". - Android GKI docs (source.android.com, updated Jun 2026): as much as 50% of kernel code out of tree; "a delay of up to 18 months from the point where an LTS release was available upstream, to when it was in a device"; 90% of the kernel security issues reported in the Android Security Bulletin had already been fixed for devices that stay up to date. - ChromeOS "Upstream First": driver patches must be accepted upstream first. LWN, Sep 2019, Doug Anderson: "We're trying not to do what Android did 10 years ago." Ask the room: how many internal patches does your team carry? [TIMING: 75s.]
